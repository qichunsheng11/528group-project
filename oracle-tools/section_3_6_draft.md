## 3.6 Oracle evidence workflow

The inspection Oracle is a permissioned signer that attests to one external fact per agreement: whether a move-out inspection passed or failed. The Oracle does not operate as an autonomous data network, does not aggregate multiple sources, and does not reach consensus. A human inspector conducts the inspection off-chain, produces a written report, and the Oracle signer submits the result and a SHA-256 hash of that report to the RentalEscrow contract on-chain. The Oracle holds ORACLE_ROLE and may call only `recordInspection`; it cannot create agreements, fund deposits, propose or accept settlements, raise disputes, resolve disputes, or withdraw balances.

### 3.6.1 Trusted signer and key custody

The Oracle is represented by a single authorised Ethereum address. In Sepolia mode the private key for this address is stored in a local `.env` file that is excluded from version control via `.gitignore`. No private key material appears in the repository, in build output, or in any report attachment. The Oracle address is granted `ORACLE_ROLE` by the contract deployer (Member B) after deployment using `grantRole(ORACLE_ROLE, oracleAddress)`. The deployer retains the `DEFAULT_ADMIN_ROLE` and may revoke the Oracle role if the key is compromised; the admin cannot withdraw user funds.

### 3.6.2 Off-chain report storage and hash algorithm

The full inspection report is stored off-chain. For the course prototype, synthetic report documents are stored as plain-text files in the repository under `oracle-tools/`. The report content includes the agreement ID, property identifier, inspection date, inspector identity, a condition checklist, and the overall result. In a production system the report would be encrypted and stored on IPFS or a controlled-access storage service; only the integrity hash would be written on-chain.

The hash algorithm is SHA-256. The hash is computed over the raw bytes of the report file using a utility script (`hash_report.py`). The resulting 32-byte digest is formatted as a `0x`-prefixed 64-character hexadecimal string, matching the Solidity `bytes32` type expected by `recordInspection`. No secondary keccak hashing or encoding transformation is applied — the same raw bytes that produce the hash are the bytes that an independent verifier would hash to reproduce it.

|---|---|
| Report storage location | `oracle-tools/sample_report_passed.txt`, `oracle-tools/sample_report_failed.txt` (synthetic) |
| Hash algorithm | SHA-256, applied to raw file bytes, output as `bytes32` |

### 3.6.3 Allowed Passed/Failed update policy

The contract accepts inspection updates only when the following conditions are met:

1. The caller holds `ORACLE_ROLE`.
2. The `reportHash` is non-empty (not `bytes32(0)`).
3. The agreement status is not `Settled` or `Cancelled`.

When these conditions hold, the Oracle may record either `Passed` (`bool passed = true`) or `Failed` (`bool passed = false`). The contract stores the current inspection record in a mapping; each update overwrites the previous record in storage, but every update is permanently retained in the event log via `InspectionRecorded`. The Oracle cannot write `NotRequested` — that value is the default state of a newly created agreement and cannot be reasserted once a result has been recorded. An inspection update never triggers settlement, never changes the agreement status, and never modifies the withdrawal balances assigned to either party.

### 3.6.6 Limitations and trust boundary

The Oracle is a trusted reporter. A SHA-256 hash anchored on-chain proves that a specific report file existed and has not been modified since the `recordInspection` transaction was mined. The hash does not prove that the report content is true, that the inspection was conducted competently, or that the property condition described in the report is accurate. A compromised Oracle signing key could submit a false inspection result; this risk is mitigated by role separation, immutable event history, and the fact that an Oracle update cannot move funds — but it cannot be eliminated by the protocol alone. The arbiter retains the authority to override any settlement allocation regardless of the inspection record. These limitations are design constraints, not defects, and are consistent with the threat model documented in Section 5.2.
